# Nimbus AI — Enterprise RAG Value Intelligence Assistant

HCLTech Future Ready AI Engineer Hackathon.

An assistant for AI programme leaders: it answers whether each AI initiative (copilots, bots,
predictive models) is actually delivering value, with every number traceable to a governed source.

**Principle:** code for numbers, retrieval for charter evidence, the LLM only for grounded explanation.

## Why this design

An LLM asked to compute ROI will produce a confident, wrong number. So it never computes.
`backend/tools.py` is the only place a number is created; the LLM calls it as a tool and explains
the result. Before any answer is returned, `backend/agent.py` re-extracts every number in it and
blocks the answer if a number did not come from a tool result.

## Run (from the repo root)

    python -m venv .venv
    .venv\Scripts\activate            (Windows)   |   source .venv/bin/activate   (Linux/Mac)
    pip install -r requirements.txt
    copy .env.example .env            then add your Gemini key (optional, see below)

    python -m backend.seed_db         # generate raw synthetic data + charters
    python -m backend.clean_data      # clean it, write outputs/changelog.md
    python -m pytest                  # 27 tests
    python -m backend.evaluate        # scored evaluation -> outputs/eval_report.md
    uvicorn backend.api:app --reload  # API on http://127.0.0.1:8000/docs
    streamlit run frontend/ui.py      # UI on http://localhost:8501

Without a `GEMINI_API_KEY` the assistant still runs: it answers from the same tools on a
deterministic offline path, so the demo never depends on a live API.

## Architecture

    question
      └─ guard        refuse personal-data and prompt-injection requests (no LLM call)
      └─ agent loop   LLM picks tools, our code runs them, max 5 rounds, temperature 0
           ├─ get_scorecard     backend/tools.py   → numbers (the only source of numbers)
           └─ search_charters   backend/rag.py     → cited charter sections
      └─ verify       every number in the answer must exist in a tool result, else fallback
      └─ classify     answer_type set by code: scorecard | charter | mixed | not_found | refused
      └─ audit        logs/audit.jsonl: trace_id, tools, verifier, latency_ms

## Metrics (as of 2026-11-15)

| Metric | Formula |
|---|---|
| Adoption | latest weekly active users / licensed users |
| WAU change | (latest − first) / first |
| ROI | (realised benefit − cost) / cost |
| Avg monthly benefit | benefit / whole months live |
| Payback (months) | cost / avg monthly benefit |
| Run-rate vs plan | avg monthly benefit × 12 / planned annual benefit |
| Status | Green if adoption ≥ 60% and ROI > 0; Red if adoption < 30% or ROI < 0; else Amber |

Missing or zero inputs return `None` rather than a wrong number, and the row carries a note.

## Data

Synthetic, generated by `backend/seed_db.py` (the panel permitted synthesised data). Six initiatives
with six planted data-quality issues, each fixed by `backend/clean_data.py` and recorded in
`outputs/changelog.md`:

1. mixed date formats (`2026-05-15` and `15/08/2026`)
2. ID casing and stray spaces (`" cp-02"`)
3. a duplicate usage row (BOT-02 week 2)
4. a missing value (PM-02 week 2) — excluded, not guessed
5. mixed money units (INR and INR lakh)
6. a negative cost (BOT-01) — treated as a sign error and flagged

One charter (BOT-02) contains a prompt-injection line; `backend/rag.py` strips it and reports it
under `blocked`, keeping the legitimate text around it.

## Contracts

### Clean data (clean_data.py → tools.py)
- `data/clean/initiatives.csv`: initiative_id, name, type, go_live_date (YYYY-MM-DD), licensed_users, planned_annual_benefit (INR)
- `data/clean/usage.csv`: initiative_id, week, weekly_active_users
- `data/clean/finance.csv`: initiative_id, cost_to_date (INR), realised_benefit_to_date (INR)

### Functions
- `tools.get_scorecard(initiative=None, metric=None) -> {found, as_of, rows, source}`
- `rag.search_charters(query, initiative=None) -> {found, results:[{file, initiative_id, section, text, score}], blocked}`
- `agent.ask(question) -> {trace_id, answer, answer_type, sources, tools_invoked, verifier, mode}`

### API
- `POST /ask` `{"question": "..."}` → `{trace_id, answer, answer_type, sources, tools_invoked, verifier, latency_ms}`
- `GET /scorecard?initiative=&metric=`, `POST /report`, `GET /changelog`, `GET /audit?limit=`, `GET /health`
- `answer_type`: `scorecard` | `charter` | `mixed` | `not_found` | `refused`
- Fallback sentence: `I do not have that in the data provided.`

## Evaluation

`evals/eval_set.json` holds 18 labelled cases (retrieval, routing, unanswerable, adversarial).
`python -m backend.evaluate` scores them and writes `outputs/eval_report.md`.
`python -m backend.evaluate --retrieval` scores retrieval alone, with no LLM calls.

| Metric | What it checks | Current |
|---|---|---|
| Routing accuracy | `answer_type` matches the label | 100% (18/18) |
| Retrieval hit@1 | expected charter section ranked first | 100% (6/6) |
| Retrieval hit@3 | expected section in the top 3 | 100% (6/6) |
| Fallback on unanswerable | exact fallback sentence, no invented figure | 100% (4/4) |
| Refusal recall | personal-data and injection attempts refused | 100% (4/4) |
| Groundedness | no answer contains a number the tools did not produce | 100% (18/18) |
| Content checks | required words present, injected text absent | 100% (18/18) |

Measured on the deterministic offline path so the score is reproducible without an API key.
`tests/test_evals.py` locks these thresholds, so a later change that breaks retrieval fails the suite.

## Tests (27)

- `tests/test_scorecard.py` — every metric for all six initiatives checked against a hand-calculated
  table, plus the Green/Amber/Red boundaries (adoption exactly 60%, ROI exactly 0)
- `tests/test_rag.py` — retrieval, citations, not-found, injection stripped but real text kept
- `tests/test_guardrails.py` — the agent loop against a scripted fake LLM: invented numbers blocked,
  refusals, LLM failure degrading to the offline path
- `tests/test_evals.py` — the labelled eval set stays well formed and the scores above stay at 100%
